# StageFlow

> 버스킹·소규모 공연의 **참가곡 취합 → 공연 순서 편성 → 공연 당일 진행 관리**를 하나의 웹에서 처리하는 공연 운영 관리 서비스

StageFlow는 단순한 CRUD 포트폴리오가 아니라, 실제 동아리 버스킹 운영에서 카카오톡으로 처리하던 수작업을 웹 서비스로 옮기고 **실제 운영진과 참가자가 사용하는 것**을 목표로 합니다.

```
실제 문제 발견 → MVP 설계 → 개발 → 배포 → 실제 버스킹 운영에 적용 → 피드백 수집 → 개선
```

---

## 1. 문제: 카카오톡으로 돌아가던 버스킹 운영

버스킹 공연 약 1~2주 전부터 운영은 이렇게 진행됐습니다.

1. 참가자들이 부르고 싶은 곡을 **카카오톡 개인톡/단톡으로** 운영진에게 보냄
2. 동아리 회장이나 간부가 메시지를 하나씩 보며 **수기로 취합**
3. 운영진이 참가자와 곡 목록을 정리해 **공연 순서를 만들어 공지**
4. 공연 당일 지각·취소·추가 참가 등으로 순서가 바뀔 때마다 **전체 공지를 다시 작성**

이 과정에서 반복적으로 생기던 문제는 다음과 같습니다.

| 문제 | 결과 |
| --- | --- |
| 참가곡을 운영진이 직접 취합 | 누락·오타, 운영진 업무 부담 |
| 곡 수정 요청을 다시 받아 반영 | 어떤 버전이 최신인지 혼동 |
| 순서 공지가 여러 번 올라옴 | 참가자가 최신 순서를 헷갈림 |
| 당일 변경마다 공지를 새로 작성 | 공연 진행 중 운영진이 공지에 묶임 |
| 참가자가 자기 순서를 직접 확인하기 어려움 | "저 몇 번째예요?" 같은 반복 문의 |

## 2. StageFlow가 대신하는 것

StageFlow는 위 과정을 하나의 웹 서비스로 통합합니다.

| 단계 | 기존 방식 | StageFlow |
| --- | --- | --- |
| **참가곡 모집** | 카톡으로 받은 곡을 수기로 정리 | 행사 링크로 참가자가 직접 제출 · 수정 |
| **공연 순서 편성 · 공개** | 엑셀/메모로 순서 작성 후 공지 | 관리자 화면에서 Drag & Drop으로 편성하고 버튼 하나로 공개 |
| **공연 당일 진행** | 변경될 때마다 공지 재작성 | 관리자가 상태를 바꾸면 참가자 화면에 실시간 반영 |
| **앵콜** | 현장에서 말로 받아 다시 정리 | 관리자가 앵콜을 열면 참가자가 링크에서 바로 신청 |

### 행사 진행 단계

행사는 아래 단계를 순서대로 지나갑니다. **단계는 관리자만 바꿀 수 있고**, 바뀌는 즉시 참가자 화면의 메인과 할 수 있는 일이 함께 바뀝니다.

```
준비 → 모집 중 → 모집 마감 → 순서 공개 → 공연 중 → 앵콜 → 종료
DRAFT   OPEN      CLOSED      PUBLISHED   LIVE      ENCORE   ENDED
```

| 단계 | 참가자 메인 화면 | 참가자가 할 수 있는 일 | 관리자가 다음 단계로 |
| --- | --- | --- | --- |
| **준비** `DRAFT` | (링크 공유 전) | — | 행사 생성 후 [모집 시작] |
| **모집 중** `OPEN` | 신청된 곡 목록 | 곡 신청, 내 신청 수정 · 삭제 (PIN) | [모집 마감] |
| **모집 마감** `CLOSED` | 신청된 곡 목록 (보기만) | 보기만 | 순서 편성 후 [순서 공개] |
| **순서 공개** `PUBLISHED` | 공연 순서 | 보기, 내 순서 확인 · 표시 | [공연 시작] |
| **공연 중** `LIVE` | 공연 순서 (실시간) | 보기, 내 순서 확인 · 표시 | 모든 순서 완료 후 [앵콜 열기] |
| **앵콜** `ENCORE` | 공연 순서 + 앵콜 신청 버튼 | 앵콜 곡 신청, 내 앵콜 곡 수정 · 취소 (PIN, 내 차례 전까지) | [공연 종료] |
| **종료** `ENDED` | 최종 셋리스트 | 보기만 | — |

### 단계별 참가자 흐름

**모집 중**

```
[참가]  신청된 곡 목록 → 곡 신청 → 제출 완료 → 신청된 곡 목록 (내 신청에 MY 표시)
[수정]  신청된 곡 목록 → 내 신청 선택 → PIN 입력 → 수정 / 삭제
```

- 신청된 곡 목록은 **공연자와 곡까지 모두 공개**합니다. 서로 어떤 곡을 내는지 보고 중복을 피할 수 있습니다.
- 한 번의 신청에 **여러 곡**을 담을 수 있고, **듀엣 · 팀**이면 함께 부르는 사람을 추가합니다. (5장)

**모집 마감 · 순서 공개**

- 모집이 마감되면 참가자는 더 이상 직접 수정할 수 없습니다. 운영진이 순서를 편성하는 동안 신청이 바뀌면 편성이 꼬이기 때문입니다.
- 운영진이 순서를 다 짜고 [순서 공개]를 누르면 참가자 메인이 **공연 순서**로 바뀝니다. 공연 전부터 자기 순서를 확인할 수 있어 "저 몇 번째예요?" 문의가 줄어듭니다.
- 순서나 곡을 바꾸고 싶은 참가자는 **운영진에게 직접** 말하고, 관리자가 반영합니다. 화면에는 "변경 요청은 운영진에게 말해주세요"라고 안내합니다.

**공연 중**

```
[내 순서]  공연 순서 → 내 신청 찾기 → 표시 (PIN 없음)
```

- 참가자는 순서와 곡을 **바꿀 수 없습니다.** 수정 · 취소 버튼 자체를 보여주지 않습니다.
- 지각 · 취소 · 현장 추가는 운영진에게 말하면 관리자가 처리합니다.

**앵콜**

```
관리자: 모든 순서 완료 → [앵콜 열기]
참가자: 공연 순서 → [앵콜 신청] → 곡 1개 제출 (솔로 · 듀엣 가능) → 제출 완료 → 공연 순서
```

- [앵콜 열기]는 모든 엔트리가 완료 또는 취소 상태일 때만 누를 수 있습니다.
- 앵콜 신청은 **한 번에 곡 하나**입니다. 같은 사람이 여러 번 신청할 수는 있습니다.
- 앵콜 순서는 **선착순**입니다. 신청하는 즉시 앵콜 순서 맨 뒤에 자동으로 배정됩니다. (앵콜 안에서 `01`, `02` …로 다시 번호를 매깁니다.)
- 앵콜 신청에도 **수정 PIN 4자리**를 받습니다. 참가자는 **자기 차례가 시작되기 전까지** PIN으로 곡 · 아티스트 · 함께 부르는 사람을 직접 바꾸거나 신청을 취소할 수 있습니다.
- 단, **순서는 참가자가 바꿀 수 없습니다.** 순서를 미루고 싶으면 운영진에게 말하고 관리자가 옮깁니다.

## 3. 사용자 역할

StageFlow의 사용자는 **관리자**와 **일반 참가자** 두 종류뿐입니다.

| | 관리자 (운영진) | 일반 참가자 |
| --- | --- | --- |
| 대상 | 동아리 회장, 간부, 버스킹 운영진 | 버스킹에 참가하는 누구나 |
| 로그인 | **필요** (Supabase Auth) | **불필요** |
| 접근 경로 | 관리자 화면 | 공유받은 행사 링크 `/events/{publicCode}` |
| 할 수 있는 일 | 행사 생성, 행사 단계 전환, 신청 목록 관리, 신청 수정 · 삭제 · 추가, 참가 취소 처리, 순서 편성 · 변경 · 공개, 현재 공연자 지정, 공연 완료 처리, 앵콜 열기 · 관리 | 참가곡 신청, 모집 중 내 신청 수정 · 삭제 (PIN), 신청된 곡 목록 · 공연 순서 · 현재 공연자 · 다음 공연자 · 내 순서 확인, 앵콜 신청 · 수정 (PIN) |

계정 시스템은 **운영진 인증에만** 사용합니다. 일반 참가자용 회원 테이블이나 Supabase Auth 계정은 만들지 않습니다.

참가자가 무엇을 할 수 있는지는 화면뿐 아니라 **서버에서도 행사 단계로 다시 확인**합니다. 예를 들어 `OPEN`이 아닌 단계의 본 공연 신청 수정, `ENCORE`가 아닌 단계의 앵콜 신청, 이미 공연이 시작된 앵콜 곡의 수정은 서버가 거부합니다.

## 4. 왜 일반 참가자에게 로그인을 요구하지 않는가

> **불필요한 회원가입과 로그인을 요구하지 않는 것**이 StageFlow의 가장 중요한 UX 원칙입니다.

- 참가자는 행사 하나에 **곡을 내러** 들어옵니다. 이 목적에 회원가입은 과한 절차입니다.
- 링크는 카카오톡 단톡방에서 공유됩니다. **링크를 누르면 바로 신청할 수 있어야** 기존 카톡 방식보다 편하다고 느낍니다.
- 가입 절차가 생기면 참가자가 다시 카톡으로 곡을 보내게 되고, 운영진의 수작업이 그대로 돌아옵니다.
- 공연 순서는 공연을 보러 온 관객도 확인할 수 있어야 하므로 조회에도 로그인이 없어야 합니다.

```
관리자            → 로그인 필요
일반 참가자       → 로그인 불필요
공연 순서 조회자  → 로그인 불필요
```

## 5. 참가 신청과 수정 PIN

### 한 번의 신청 = 공연자 + 여러 곡

참가자는 한 번의 신청에 **공연자**와 **부를 곡들**을 함께 냅니다.

```
공연 형태:   듀엣 · 팀
공연자:     신승빈, 이명우
곡:         01  연인 — 박효신
            02  한 페이지가 될 수 있게 — DAY6
수정 PIN:   4829
```

- 공연자는 신청 안의 **모든 곡을 함께 부릅니다.** 솔로면 공연자가 한 명입니다.
- 공연 순서는 **곡마다 따로** 잡힙니다. 위 신청은 공연 순서에 두 칸으로 들어갑니다.
- 수정 PIN은 **신청 하나에 하나**이며, 그 신청의 모든 곡에 공통입니다.
- 함께 부르는 사람은 따로 신청하지 않아도 됩니다. 그래도 같은 곡이 중복되면 관리자가 정리합니다.

### 동작 원리

- 각 신청(`submissions`)은 DB 내부 고유 PK(`id`)를 가집니다.
- 수정 · 삭제할 때는 **`submissionId + editPin` 조합**으로 권한을 확인합니다.
- PIN은 신청을 *찾는* 키가 아니라, 그 신청을 *수정할 자격*이 있는지 확인하는 인증 값입니다.
- 그래서 **PIN은 고유할 필요가 없습니다.**

```
Submission 37 / PIN 0000   ← 서로 다른 신청이므로
Submission 52 / PIN 0000   ← 같은 PIN이어도 충돌하지 않음
```

### 보안 원칙

> PIN의 목표는 "완벽한 방어"가 아니라 **실수로 남의 신청을 고치거나 가벼운 장난을 치는 것을 막는 수준**입니다. 문제가 생겨도 관리자가 신청을 직접 수정할 수 있으므로, 참가자 경험을 해치는 무거운 장치(시도 횟수 제한, 잠금 등)는 두지 않습니다.

- PIN은 **숫자 4자리**입니다. 공연 당일 현장에서도 쉽게 기억하고 입력할 수 있는 길이를 택했습니다.
- PIN 원문은 저장하지 않고 **해시로만 저장**합니다.
- PIN 해시는 공개 데이터와 분리된 **`submission_secrets` 테이블**에 저장합니다.
- PIN 검증은 클라이언트가 아닌 **서버 측(Next.js Server Action / Route Handler)에서만** 수행합니다.
- PIN으로 수정 · 삭제할 수 있는 때는 정해져 있습니다.
  - 본 공연 신청: **모집 중(`OPEN`)**일 때만
  - 앵콜 신청: **앵콜(`ENCORE`)** 중, 그 곡의 차례가 시작되기 전까지
- 기기에 종속되지 않습니다. 다른 휴대폰이나 PC에서도 신청된 곡 목록에서 자기 신청을 고르고 PIN을 입력하면 수정할 수 있습니다.

### 왜 PIN 해시를 별도 테이블로 분리했는가

참가자 페이지는 로그인 없이 신청 · 공연 순서를 조회하고 Realtime으로 변경을 구독합니다. 그러려면 이 테이블들에 **공개(anon) 읽기 권한**이 필요합니다.

그런데 Supabase RLS는 **행 단위**로 접근을 제어합니다. PIN 해시가 같은 테이블에 있으면 공개 조회 응답이나 Realtime 변경 메시지에 해시 컬럼이 함께 실려 나갈 수 있습니다. 4자리 PIN은 경우의 수가 1만 개뿐이라, 해시가 노출되면 오프라인에서 즉시 역산됩니다.

그래서 테이블 자체를 나눴습니다.

| 테이블 | 공개(anon) 접근 | 용도 |
| --- | --- | --- |
| `submissions`, `performance_entries` | 읽기 허용 + Realtime 구독 | 신청된 곡 목록, 공연 순서, 현재 공연자 표시 |
| `submission_secrets` | **접근 불가** (RLS 정책 없음) | 서버에서 PIN 검증할 때만 사용 |

공개 테이블에는 처음부터 민감한 값이 없으므로, 조회 쿼리나 Realtime 설정을 실수해도 PIN 해시가 새어 나가지 않습니다.

### 수정 흐름

```
신청된 곡 목록 → 내 신청 선택 → PIN 입력
  → 서버로 submissionId + PIN 전송
  → 서버가 수정 가능한 때인지 확인 (본 공연 신청은 OPEN, 앵콜 신청은 ENCORE이면서 공연 시작 전)
  → 서버가 submission_secrets에서 해시 조회 → PIN 해시 비교
  → 일치: 서버가 신청과 곡들을 수정/삭제 / 불일치: 거부
```

## 6. 공연 순서의 실시간 반영

공연 당일 관리자는 StageFlow 관리자 화면을 켜 두고 진행 상황을 관리합니다.

- 현재 공연자 지정 → 공연 완료 처리 → 다음 공연자 확인
- 순서 변경, 중간 참가자 삽입, 참가 취소, 현장 상황에 따른 재배치
- 행사 단계 전환 (순서 공개, 공연 시작, 앵콜 열기, 종료)

관리자가 순서 · 상태 · 행사 단계를 바꾸면 **Supabase Realtime**이 해당 행사를 구독 중인 참가자 페이지로 변경을 전달하고, 참가자 페이지는 새로고침 없이 갱신됩니다.

```
관리자: "3번 공연 완료, 4번 PERFORMING"
   ↓ DB 업데이트 (performance_entries)
   ↓ Supabase Realtime
참가자 페이지: 현재 공연자 / 다음 공연자 / 전체 순서 즉시 갱신

관리자: [앵콜 열기]
   ↓ DB 업데이트 (events.status = ENCORE)
   ↓ Supabase Realtime
참가자 페이지: 앵콜 신청 버튼 등장

참가자: 앵콜 신청
   ↓ 서버가 앵콜 순서 맨 뒤에 배정 (선착순)
   ↓ Supabase Realtime
모든 참가자 페이지: 앵콜 순서에 새 곡 추가
```

이제 운영진은 공지를 다시 쓰지 않아도 되고, 참가자는 링크 하나로 항상 최신 순서를 봅니다.

### 로그인 없이 "내 순서" 표시하기

참가자 계정이 없어도 신청된 곡 목록과 공연 순서 화면에서 **내 신청에 `MY` 표시**와 **내 순서까지 남은 팀 수**를 보여줍니다.

1. 신청을 제출하면 서버가 새 신청의 `submissionId`를 돌려줍니다.
2. 브라우저가 이를 행사별로 `localStorage`에 저장합니다. (예: `stageflow:{publicCode}` → `[37]`)
3. 같은 브라우저로 행사 링크를 다시 열면, 저장된 신청에 속한 곡들을 모두 내 순서로 표시합니다.

서버에는 아무것도 저장하지 않습니다. 신청 목록과 공연 순서는 원래 공개 정보이므로 "어느 줄이 내 것인지 표시"하는 데에는 인증이 필요 없습니다.

#### 저장이 사라지는 경우와 보완

버스킹 참가자는 대부분 **폰의 카카오톡 인앱 브라우저**로 제출하고, 공연 당일에도 같은 단톡방 링크로 들어오므로 대부분 그대로 표시됩니다. 다만 다음 경우에는 저장된 값이 없습니다.

- 카카오톡에서 "다른 브라우저로 열기"를 하거나 링크를 Chrome · Safari에 붙여 넣은 경우 (브라우저마다 저장소가 따로임)
- 제출부터 공연까지 1~2주 사이에 브라우저나 OS가 저장 데이터를 지운 경우 (iOS의 장기 미방문 사이트 데이터 정리, 카카오톡 캐시 정리 등)

그래서 두 가지를 함께 둡니다.

- **내 신청 찾기**: 표시가 없으면 목록에서 자기 신청을 골라 다시 저장합니다. 표시용이라 **PIN 없이** 고를 수 있습니다. 남의 신청을 골라도 자기 화면 표시만 바뀌고 데이터는 바뀌지 않습니다.
- **제출 완료 안내**: "공연 당일에도 이 단톡방 링크로 들어오세요"라고 안내해 다른 브라우저로 여는 경우를 줄입니다.

> **보기**는 자유롭게, **바꾸기**(수정 · 삭제)는 PIN으로 나눕니다.

## 7. 데이터 모델

```
Event 1 ── N Submission 1 ── N PerformanceEntry
                 └── 1 SubmissionSecret
```

### `events`

| 필드 | 설명 |
| --- | --- |
| `id` | PK |
| `title` | 행사명 |
| `event_date` | 공연 일자 |
| `venue` | 장소 |
| `public_code` | 공개 링크용 코드 (`/events/{publicCode}`) |
| `status` | 행사 진행 단계 (`DRAFT` · `OPEN` · `CLOSED` · `PUBLISHED` · `LIVE` · `ENCORE` · `ENDED`) |
| `created_at` / `updated_at` | 생성 · 수정 시각 |

### `submissions`

참가자가 한 번에 낸 **신청 묶음**입니다. 공연자와 PIN의 단위입니다.

| 필드 | 설명 |
| --- | --- |
| `id` | PK (PIN 검증 시 함께 사용) |
| `event_id` | FK → `events.id` |
| `performer_names` | 공연자 이름 목록 (솔로면 1명, 듀엣 · 팀이면 여러 명) |
| `is_encore` | 앵콜 신청 여부 |
| `created_at` / `updated_at` | 생성 · 수정 시각 |

### `performance_entries`

신청 안의 **곡 하나 = 공연 순서의 한 칸**입니다.

| 필드 | 설명 |
| --- | --- |
| `id` | PK |
| `event_id` | FK → `events.id` |
| `submission_id` | FK → `submissions.id` (신청 삭제 시 함께 삭제) |
| `artist` | 아티스트명 |
| `song_title` | 곡 제목 |
| `order_index` | 공연 순서 (편성 전에는 `null`) |
| `status` | 엔트리 상태 |
| `created_at` / `updated_at` | 생성 · 수정 시각 |

`submissions`와 `performance_entries`는 공개 조회와 Realtime 구독 대상이므로 **민감한 값을 두지 않습니다.**

### `submission_secrets`

신청의 수정 PIN 해시만 따로 보관합니다. 공개 접근이 막혀 있고 서버에서만 읽습니다.

| 필드 | 설명 |
| --- | --- |
| `submission_id` | PK, FK → `submissions.id` (신청 삭제 시 함께 삭제) |
| `edit_pin_hash` | 수정 PIN(숫자 4자리) 해시 (원문 저장 안 함) |
| `created_at` / `updated_at` | 생성 · 수정 시각 |

본 공연 신청과 앵콜 신청 모두 PIN을 가집니다.

### 엔트리 상태

```
SUBMITTED → SCHEDULED → PERFORMING → COMPLETED
     └──────────┴──────────→ CANCELLED
```

| 상태 | 의미 |
| --- | --- |
| `SUBMITTED` | 곡 제출됨, 순서 미편성 (`order_index = null`) |
| `SCHEDULED` | 공연 순서에 배치됨, 대기 중 |
| `PERFORMING` | 현재 공연 중 |
| `COMPLETED` | 공연 완료 |
| `CANCELLED` | 참가 취소 |

## 8. 기술 스택

| 영역 | 기술 |
| --- | --- |
| Framework | Next.js (App Router) |
| Language | TypeScript |
| Styling | Tailwind CSS |
| Database | Supabase PostgreSQL |
| Auth | Supabase Auth (관리자 전용) |
| Realtime | Supabase Realtime |
| Deployment | Vercel |

```
사용자 → Next.js + TypeScript (Vercel) → Supabase (PostgreSQL · Auth · Realtime)
```

### 왜 Next.js인가

Supabase가 DB·인증·Realtime을 맡지만, 로그인 없는 참가자를 다루려면 **신뢰할 수 있는 서버 계층**이 필요합니다.

- **PIN 검증**: 참가자는 Supabase Auth 계정이 없으므로 RLS만으로는 "이 신청의 주인인가"를 판단할 수 없습니다. Server Action / Route Handler에서 `submission_secrets`의 해시를 비교한 뒤에만 수정·삭제를 실행합니다.
- **카카오톡 링크 미리보기**: 행사 링크를 단톡방에 공유했을 때 행사별 제목·날짜가 미리보기에 보이도록 서버에서 메타데이터를 생성합니다.
- **Vercel 배포**: 별도 설정 없이 프론트엔드와 서버 로직을 함께 배포합니다.

관리자 화면과 실시간 공연 순서 화면은 클라이언트 컴포넌트에서 Supabase에 직접 연결합니다.

## 커밋 · PR 규칙

커밋 메시지는 `type: 제목` + 빈 줄 + `- 변경사항` 목록으로 작성합니다.

```
feat: 참가곡 제출 폼 및 수정 PIN 검증 추가

- submission_secrets 테이블에 PIN 해시 저장
- Server Action에서 submissionId + PIN 검증
```

| type | 용도 |
| --- | --- |
| `feat` | 기능 추가 (UI 디자인 변경 포함) |
| `fix` | 버그 수정 |
| `refactor` | 동작이 같은 구조 개선 |
| `chore` | 설정, lockfile, CI |
| `docs` | 문서 |
| `style` | 포맷, lint |
| `test` | 테스트 코드 |

클론 후 한 번만 실행하면 커밋할 때 규칙을 자동으로 검사합니다.

```bash
git config core.hooksPath .githooks && git config commit.template .gitmessage
```

`main` 외 브랜치에 push하면 GitHub Actions(`commit-lint`)가 같은 규칙을 다시 검사합니다. PR 본문은 `.github/pull_request_template.md` 양식을 따릅니다.
